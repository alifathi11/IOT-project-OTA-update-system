# هفته اول — سرور و پنل مدیریتی

<div dir="rtl">

این فایل توضیح کاری است که در هفته اول روی سمت سرور و پنل انجام شد.

- **سرور و پایگاه داده:** آرمین فارسی
- **پنل تحت وب:** امیررضا بهرامی

سمت برد (ESP32) کار علی است و در این متن واردش نشدیم.

## چه چیزی ساخته شد

یک سرور FastAPI با پایگاه داده SQLite که هر ده مسیر قرارداد API را پیاده کرده، به‌علاوه یک پنل ساده با HTML/CSS/JS که همان سرور آن را سرو می‌کند. پنل روی `/panel/` بالا می‌آید و چون از همان آدرس سرو می‌شود، درگیر CORS نشدیم.

عملیات کامل OTA و rollback واقعی روی برد جزو کار هفته اول نبود، ولی سرور و پایگاه داده از همین حالا وضعیت‌های `rolled_back` و `failed` را می‌فهمند تا هفته بعد فقط سمت برد بماند.

## ساختار پوشه‌ها

```
src/server/
  app/
    main.py        نقطه ورود، mount کردن پنل و روترها
    db.py          اتصال SQLite و ساخت جدول‌ها
    schema.sql     تعریف جدول‌ها و ایندکس‌ها
    config.py      مسیر فایل‌ها و تنظیمات
    schemas.py     مدل‌های ورودی (Pydantic)
    helpers.py     محاسبه SHA-256، مقایسه نسخه، پیدا کردن دستگاه
    routers/       devices.py / firmwares.py / updates.py
  scripts/         راه‌اندازی، اجرا، پاک کردن دیتابیس
  storage/         فایل دیتابیس و باینری‌های آپلودشده

src/web_panel/
  index.html       صفحه Devices
  firmwares.html   صفحه Firmware
  updates.html     صفحه Update
  history.html     صفحه History
  js/api.js        کلاینت API و چند تابع کمکی مشترک
  css/style.css
```

## پایگاه داده

همان چهار جدولی که در برنامه هفته اول تعریف شده بود، بدون تغییر: `firmwares`، `devices`، `update_jobs` و `update_events`. ایندکس‌ها هم روی همان ستون‌هایی زده شد که در برنامه آمده بود.

چند نکته که موقع پیاده‌سازی اضافه شد:

- فایل firmware روی دیسک در `storage/firmwares/` می‌ماند و فقط مشخصاتش داخل دیتابیس ثبت می‌شود.
- روی `sha256` یک `CHECK` گذاشتیم که طولش دقیقا ۶۴ کاراکتر باشد، تا هش ناقص وارد جدول نشود.
- روی `update_mode` و `status` هم `CHECK` گذاشته شد که فقط مقدارهای مجاز قابل درج باشند. این کار جلوی خیلی از اشتباهات تایپی سمت کلاینت را می‌گیرد.
- کلیدهای خارجی با `ON DELETE CASCADE` تعریف شدند تا با حذف یک دستگاه، تاریخچه‌اش هم آواره نماند.

## APIها

هر ده مسیر قرارداد پیاده شد. مصرف‌کننده هر کدام همان است که در برنامه هفته اول مشخص شده بود.

| مسیر | کار |
| --- | --- |
| `POST /api/devices/register` | ثبت دستگاه یا heartbeat |
| `GET /api/devices/{id}/update?version=x` | برد می‌پرسد نسخه جدیدی هست یا نه |
| `GET /api/firmwares/{id}/download` | دریافت فایل باینری |
| `POST /api/updates/{id}/status` | گزارش هر مرحله از طرف برد |
| `GET /api/devices` | فهرست دستگاه‌ها برای پنل |
| `GET /api/firmwares` | فهرست نسخه‌ها |
| `POST /api/firmwares` | آپلود نسخه جدید |
| `POST /api/devices/{id}/update` | به‌روزرسانی دستی از پنل |
| `PATCH /api/devices/{id}/mode` | تعیین حالت دستی یا خودکار |
| `GET /api/updates?device_id={id}` | تاریخچه به‌روزرسانی |

چند تصمیمی که سر راه گرفتیم:

**آدرس‌دهی دستگاه.** پنل دستگاه را با `id` عددی می‌شناسد ولی برد فقط `device_uid` خودش را دارد. به‌جای اینکه دو دسته مسیر جدا بسازیم، تابع `find_device` هر دو را قبول می‌کند؛ اگر ورودی عدد بود اول با `id` می‌گردد و بعد سراغ `device_uid` می‌رود.

**محاسبه هش در سرور.** هنگام آپلود، فایل chunk به chunk خوانده و SHA-256 آن حساب می‌شود. همان هش در پاسخ بررسی نسخه به برد داده می‌شود تا قبل از نصب صحت فایل را چک کند.

**حالت خودکار.** اگر دستگاه روی `automatic` باشد و کار در صف نداشته باشد، خود سرور موقع بررسی نسخه جدیدترین firmware فعال را پیدا می‌کند و یک job می‌سازد. مقایسه نسخه‌ها متنی نیست؛ `1.2.10` به عدد تبدیل می‌شود وگرنه از `1.2.9` کوچک‌تر حساب می‌شد.

**تغییر نسخه دستگاه.** فقط وقتی `success` گزارش شود نسخه فعلی دستگاه عوض می‌شود، و با `rolled_back` به `from_version` برمی‌گردد. تا قبل از آن دستگاه هنوز روی نسخه قدیمی است، پس بی‌خود جلو نمی‌بریمش.

**قفل کردن job تمام‌شده.** روی یک job که به `success` یا `failed` یا `rolled_back` رسیده دیگر نمی‌شود وضعیت جدید ثبت کرد و ۴۰۹ برمی‌گردد. همین‌طور تا وقتی یک job باز است، job دوم برای همان دستگاه ساخته نمی‌شود.

## پنل

چهار صفحه با همان اسم‌هایی که در برنامه آمده بود:

- **Devices** — فهرست دستگاه‌ها با شناسه، نسخه فعلی، وضعیت آخرین به‌روزرسانی و زمان آخرین ارتباط. هر ده ثانیه خودش refresh می‌شود و یک نقطه سبز/خاکستری نشان می‌دهد دستگاه اخیرا خبری داده یا نه. حالت دستی/خودکار را هم از همین‌جا می‌شود عوض کرد.
- **Firmware** — فرم آپلود نسخه جدید به‌همراه توضیح تغییرات، و جدول نسخه‌های موجود با حجم و هش.
- **Update** — انتخاب دستگاه و نسخه مقصد و ساختن job، به‌علاوه فهرست کارهای در جریان.
- **History** — تاریخچه job ها با قابلیت فیلتر روی یک دستگاه. زیر هر job تمام مرحله‌هایی که برد گزارش داده با زمان و پیامشان دیده می‌شود.

کد پنل عمدا بدون فریم‌ورک نوشته شد. `js/api.js` تمام فراخوانی‌ها را نگه می‌دارد و بقیه فایل‌ها فقط render می‌کنند. گوشه بالا-راست هم وضعیت اتصال به سرور را نشان می‌دهد که همان تست ارتباط پنل با API است.

## اجرا

```bash
cd src/server
bash scripts/01_setup.sh     # ساخت venv و نصب وابستگی‌ها
bash scripts/02_run.sh       # اجرای سرور روی پورت ۸۰۰۰
```

بعدش:

- پنل: <http://localhost:8000/panel/>
- مستندات خودکار API: <http://localhost:8000/docs>

برای پاک کردن دیتابیس و فایل‌های آپلودشده `bash scripts/03_reset_db.sh`.

برای اینکه برد بتواند وصل شود، سرور باید روی `0.0.0.0` بالا بیاید (که پیش‌فرض همین است) و برد از IP سیستم در شبکه محلی استفاده کند، نه `localhost`.

## تست

کل مسیر با curl تست شد: ثبت دستگاه، آپلود دو نسخه، ساختن job از پنل، دانلود فایل و مقایسه هش، گزارش مرحله‌ها تا `success` و بعد سناریوی `failed` و `rolled_back`. هش فایل دانلودشده با هش سرور و با فایل اصلی یکی بود. حالت‌های خطا (نسخه تکراری، دستگاه ناموجود، job بسته) هم همان کد وضعیتی را برمی‌گردانند که باید.

یک باگ هم همین‌جا پیدا شد: اتصال SQLite در پایتون به thread گره خورده است و FastAPI ممکن است باز کردن و استفاده از اتصال را روی دو thread مختلف انجام دهد. با curl معلوم نمی‌شد چون درخواست‌ها پشت‌سرهم بودند، ولی پنل که دو درخواست را هم‌زمان می‌فرستاد خطای ۵۰۰ گرفت. با `check_same_thread=False` حل شد — هر درخواست همچنان اتصال خودش را دارد. بعد از اصلاح، ۷۵ درخواست هم‌زمان بدون خطا جواب داد.

## چیزهایی که ماند برای بعد

- نصب واقعی و rollback روی خود برد
- احراز هویت؛ فعلا هیچ مسیری محافظت نشده
- CORS الان روی `*` باز است که برای توسعه اشکالی ندارد ولی برای تحویل نهایی باید محدود شود
- صفحه‌بندی برای وقتی تعداد دستگاه‌ها و job ها زیاد شد
